# Canonical and support diagnostics

Canonical `DiagnosticEnvelope` chains describe semantic results. Records require meaningful explanatory notes, a structured `details` object and nullable `occurrence_metadata`. The canonical semantic digest covers exactly diagnostic kind, disposition, rules, severity, stage, subject, summary, notes and details under compact sorted UTF-8 JSON. `APS-DIAG-` plus the first 24 uppercase SHA256 characters identifies those facts; schema, chain placement, sequence and occurrence metadata are outside that digest. Invalid vocabulary, malformed ancestry and stale identities reject.

`RecoveryEngine::containment_record()` and `safe_halt_record()` expose typed projections with original/action diagnostics, the complete causal chain, typed trigger and action-specific metadata. `Diagnostics::serialize_transport` overloads export the complete canonical containment/halt transports. UTC `containment_time` and `halt_time` describe this engine's entry/adoption and do not affect semantic identity. A prevented contained operation remains blocked audit evidence. A caller-confirmed breach enters frozen terminal halt; later engine calls return the same terminal diagnostic.

Adopting valid external terminal evidence uses `POLICY_HALT_REQUEST` for local enforcement and local adoption time. It does not invent an unknown external trigger/time. Invalid imported graphs or terminal actions throw before adoption changes the engine. Earlier independent histories remain available through `retained_diagnostic_chains()`; export each separately with `Diagnostics::serialize_chain()`, rather than inventing a causal link between different roots.

Separate support `Session`/`Snapshot` evidence records explicitly supplied lifecycle, operation and fault observations; it cannot alter semantic decisions or substitute for full canonical safety transports.

Development and Release use different compiled collector implementations. Actual rich state/duration, all-context and error-message/cause collection lives only in the Debug source. Shared capture dispatches to the selected collector; Release keeps minimal Fault/Health identities, canonical references, terminal/unknown context and typed error domain/code. There is no runtime activation path for excluded rich collection. Development coverage is limited to caller-instrumented evidence; it does not capture ambient activity, arbitrary memory, stacks or an automatic crash flush. Typed allowlisted fields and Public/Personal/Secret classification apply before retention and again before export. Applications classify data at its owning boundary; do not submit credentials or sensitive data as Public.

Bounds are 4096 retained events, 4 MiB retained accounting, 16 KiB per event and 8 MiB per exported file, with essential fault reserve and visible health/drop counters. Snapshot ownership is immutable and independent. Capture/snapshot/close can run concurrently; destruction requires joining operations.

Export requires an explicit existing absolute directory without traversal/reparse points. It reserves a new child, flushes matching JSON/Markdown and creates COMPLETED.json only after both are durable. Invalid paths, denied access, cancellation, write/rename failures and bounds return explicit errors. Export is opt-in, not automatic telemetry.

Retain the paired files and completion marker together. Inspect incident/correlation IDs, expected/observed facts, supported findings, hypotheses and unknown evidence separately. Release qualification includes privacy/bounds/error/concurrency tests and full retained-field equivalence checks.
